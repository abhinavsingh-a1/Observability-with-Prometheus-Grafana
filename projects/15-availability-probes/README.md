# 15 · Availability: Targets, Synthetic Probes & TLS Certificates

> **Is it up, from the outside, the way a user would see it?**

| | |
|---|---|
| **Layer** | Availability (outside-in) |
| **Method** | Black-box monitoring |
| **Data source** | `up` (generated by Prometheus for every target) and blackbox_exporter (`probe_*`) |
| **Files** | `alerts.yml` · `dashboard.json` · `trigger.sh` · `blackbox/blackbox.yml` · blackbox jobs in `prometheus/prometheus.yml` |
| **Time** | ~15 min |

## 1. Why this matters

Everything in projects 01–14 is **white-box**: the system reports on itself. But:

- A crashed service reports nothing. **Absence of data isn't an alert** unless you make it one.
- A service can be internally "healthy" while users can't reach it: DNS, TLS, firewall, load balancer, or a wrong route.
- **Expired TLS certificates** still cause major outages every year at large companies.

Black-box monitoring tests the system like a user does: send a request, check the answer.

| Signal | Answers |
|---|---|
| `up` | Can Prometheus scrape the target? (process alive, network OK, /metrics works) |
| `probe_success` | Does the endpoint answer correctly? (status 2xx, TLS valid, DNS resolves...) |
| `probe_ssl_earliest_cert_expiry` | When does the certificate chain expire? |

## 2. How it works

**`up`:** after every scrape, Prometheus writes `up{job, instance}` = 1 (success) or 0 (failure). It's free, and it's the most important alert in any setup: if a target is down, all its other alerts go silent.

**blackbox_exporter** uses the multi-target pattern:

```
Prometheus ──GET /probe?module=http_2xx&target=https://example.com──▶ blackbox_exporter ──HTTPS──▶ example.com
           ◀──────────── probe_success, probe_duration_seconds, probe_http_status_code, probe_ssl_* ─────
```

The `relabel_configs` in `prometheus.yml` turn each listed target into the `target` URL parameter, and point `__address__` at the exporter.

| Job | Module | Targets |
|---|---|---|
| `blackbox-http` | `http_2xx` | Demo `/healthz` endpoints, Grafana health, prometheus.io, example.com |
| `blackbox-cert` | `http_2xx_insecure` | expired.badssl.com (**deliberately expired**), prometheus.io |
| `blackbox-tcp` | `tcp_connect` | Grafana, Prometheus, Alertmanager ports |
| `blackbox-icmp` | `icmp` | 1.1.1.1, 8.8.8.8 (ping) |
| `blackbox-dns` | `dns_prometheus_io` | Resolves prometheus.io through 1.1.1.1 and 8.8.8.8 |

External targets need internet access from Docker.

## 3. Key metrics

| Metric | Meaning |
|---|---|
| `up` | Scrape success |
| `probe_success` | Probe passed |
| `probe_duration_seconds` | Total probe time |
| `probe_http_status_code` | HTTP status |
| `probe_http_duration_seconds{phase}` | resolve / connect / tls / processing / transfer |
| `probe_ssl_earliest_cert_expiry` | Unix time of the earliest expiring cert in the chain |
| `probe_dns_lookup_time_seconds` | DNS time |
| `probe_icmp_duration_seconds{phase="rtt"}` | Ping round-trip time |

## 4. PromQL cookbook

```promql
# Everything Prometheus can't scrape
up == 0

# Failing probes
probe_success == 0

# Availability over 24h per endpoint (a synthetic SLI!)
avg_over_time(probe_success{job="blackbox-http"}[24h])

# Days until certificate expiry
(probe_ssl_earliest_cert_expiry - time()) / 86400

# Where does the time go? (DNS vs connect vs TLS vs server)
probe_http_duration_seconds{instance="https://example.com"}

# Detect a target that disappeared completely (no series at all)
absent(up{job="apps"})
```

## 5. Alerts (`alerts.yml`)

| Alert | Condition | Severity |
|---|---|---|
| `TargetDown` | `up == 0` for 1m | critical |
| `EndpointDown` | `probe_success == 0` for 1m | critical |
| `EndpointSlow` | HTTP probe > 2s for 5m | warning |
| `SSLCertExpiringSoon` | expires in < 14 days | warning |
| `SSLCertExpired` | already expired | critical (**fires on purpose** for expired.badssl.com) |

`EndpointDown` excludes the `blackbox-cert` job, because its only purpose is reading expiry dates.

## 6. Dashboard

- **Stats:** targets down, failing probes, soonest cert expiry, and slowest probe.
- **State timelines:** `up` for every target and `probe_success` for every probe. These give an instant visual history of outages.
- **Graphs:** probe duration, HTTP status codes, certificate days left, and DNS/ICMP latency.

## 7. Hands-on lab

```bash
./projects/15-availability-probes/trigger.sh down        # stop payments-api
# -> TargetDown (job=apps) + EndpointDown (payments /healthz), red bars in the timelines
./projects/15-availability-probes/trigger.sh reset

./projects/15-availability-probes/trigger.sh unhealthy   # orders /healthz -> 503
# -> ONLY EndpointDown: the process is up and scrapable, but it tells users it's unhealthy
./projects/15-availability-probes/trigger.sh reset
```

The difference between the two scenarios is the core lesson: `up` and `probe_success` measure **different things**.

## 8. Runbook

**TargetDown**

1. Is the process running? (`docker ps`, `kubectl get pods`)
2. Can Prometheus reach it? Prometheus → **Status → Targets** shows the exact scrape error: timeout, connection refused, or DNS.
3. Is `/metrics` returning 200 quickly? Huge metric payloads can cause scrape timeouts.

**EndpointDown**

1. Ask the exporter for a debug trace of the probe: `docker exec lab-prometheus wget -qO- "http://blackbox-exporter:9115/probe?module=http_2xx&target=<url>&debug=true"`. It prints every step (DNS, connect, TLS, response).
2. Classify the failure: DNS, connect, TLS, status code, or timeout. Then fix the corresponding layer.

**SSLCertExpiringSoon:** renew the certificate, then find out why automation (cert-manager, certbot) didn't. Alerting at 14 days leaves time for manual action.

## 9. Production tips & pitfalls

- Probe from **outside** your network as well (a second Prometheus, or a SaaS such as Grafana Synthetic Monitoring). An internal probe can't see an internet-facing outage.
- Probe what users actually use: the public URL through the CDN and load balancer, not the pod IP.
- Use `for: 1m` or more, and several probe locations, to avoid paging on a single lost packet.
- `absent()` is needed when targets come from service discovery. A deleted target has no `up` series at all.
